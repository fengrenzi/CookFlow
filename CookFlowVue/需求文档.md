**概述**
- **项目名称**: CookFlow2
- **目标**: 提供一个面向用户的美食/食谱社区与工具平台，支持食谱浏览、搜索、收藏、购物车、评论、书籍/专题管理、用户资料与 AI 助手，便于前端与基于 Spring Boot 的后端联调与实现。

**背景与动机**
- 复用现有前端（Vue + Pinia）逻辑，按前端需求生成完善的后端接口与数据库设计，支持搜索与推荐、内容审核与审计、AI 对话历史，以及横向扩展的性能需求。

**范围**
- 本文档覆盖功能性需求、非功能性需求、主要数据实体、接口/契约引用与验收标准；不包含具体后端实现细节（如代码级别）和运维部署脚本。

**利益相关者**
- 产品经理：需求与优先级
- 前端工程师：接口使用者
- 后端工程师：接口实现者（基于 Spring Boot）
- 数据工程/搜索工程师：ES/索引与分析管道
- 运维：部署、监控、备份

**关键术语**
- 食谱（Recipe）、食材（Ingredient）、用户（User）、评论（Comment）、收藏/喜欢（Favorite）、购物车（Cart）、书籍（Book）、AI 会话（AI Conversation）、审核日志（Moderation Log）

**功能性需求**
1. 用户与认证
   - 支持手机号/邮箱+密码注册、登录；支持 JWT 作为认证令牌。
   - 支持第三方登录占位（可扩展）。
   - 用户资料管理：头像、昵称、简介、关注/粉丝计数、积分/等级。

2. 食谱管理
   - 食谱浏览：分页、按标签/分类/作者过滤。
   - 食谱详情：原料列表、步骤、图片/视频、营养信息、来源/引用字段。
   - 食谱创建/编辑/删除：作者权限控制，支持草稿与发布状态。
   - 食谱评分与统计：收藏数、点赞数、浏览次数、评论数。

3. 食材管理
   - 食材列表与详情：营养信息、通用单位、替代建议。
   - 食材检索：模糊匹配与结构化筛选（如是否季节性、是否易过敏）。

4. 搜索与发现
   - 全文检索支持：按食谱标题、材料、步骤、标签、作者搜索。优先使用 Elasticsearch（中文分词插件：ik_max_word / jieba）；MySQL FULLTEXT 作为降级方案。
   - 推荐/发现：基于热门、相似标签和用户行为的简单推荐（事件上报供离线/实时推荐）

5. 互动（评论、收藏、点赞）
   - 评论：支持树状回复、删除、点赞。需审计与举报流程。
   - 收藏/点赞/关注：异步更新计数，支持去重与幂等。

6. 购物车（Cart）与导购（轻电商预留）
   - 支持将菜谱中的食材加入购物车，数量与单位管理。
   - 购物车项的 CRUD 与结算占位接口（不实现支付）。

7. 书籍/专题（Books）
   - 图书/专题聚合：支持书籍内的食谱集合、章节/目录、阅读状态跟踪。

8. 媒体管理
   - 图片/视频上传元数据记录（`media` 表），实际文件存储在 OSS/对象存储（外部服务）。

9. 管理与审核
   - 角色/权限体系（`roles`、`permissions`、`user_roles`）。
   - 内容审核日志与敏感词表、人工/自动审核记录（`moderation_logs`、`sensitive_words`）。
   - 举报流程与管理员处理界面 API（接口需支持分页、过滤、处理状态变更）。

10. AI 助手与对话
   - 保存用户与助手会话历史（`ai_conversations`、`ai_messages`），支持按会话导出与回溯。
   - 对话隐私与审计（关联 `audit_logs`）。

11. 统计与事件
   - 用户行为事件上报（浏览、点击、收藏、评论、转化），支持投递到消息队列（Kafka/RabbitMQ）用于离线分析/实时推荐。

**非功能性需求**
- 性能：常见读接口（食谱详情/列表、食材详情）P95 响应 < 300ms（空载）；并发目标视产品阶段设定（示例：100 RPS）。
- 可扩展性：服务应支持水平扩展，使用 Redis 缓存热点数据（食谱详情、排行榜）。
- 可用性：关键接口 SLO 99.5%（可依据环境调整）。
- 安全：密码使用安全哈希（bcrypt/argon2），所有写接口需校验认证与权限，接口对敏感字段加密或限制访问。
- 国际化：字符集 `utf8mb4`，接口设计考虑多语言扩展。
- 容灾与备份：每日增量备份、每周完整备份，数据库备份可恢复 RPO/RTO 目标需与运维协商。

**数据模型与引用**
- 详细表结构请参考仓库根目录的 [db_schema.sql](db_schema.sql)。
- API contract（Schema、路径、请求/响应示例）请参考 [openapi.yaml](openapi.yaml)。

**接口约定（概要）**
- 认证：所有需登录的接口使用 `Authorization: Bearer <token>`。
- 分页：统一采用 `page`、`size` 或 `limit`/`offset` 的分页参数，响应包含 `total` 与 `page` 信息。
- 错误码：统一 JSON 格式 { code, message, details? }，并提供文档化错误码表（后续补充）。

**验收标准**
- 所有关键功能对应的 API 在 `openapi.yaml` 中有定义并能通过 mock 或后端实现联调。
- 数据库模式与 `db_schema.sql` 能在目标 MySQL 实例中顺利执行（无语法错误）。
- 审核、AI 会话、事件上报等关键表与字段存在并能存储基本数据。

**开发与验收里程碑（建议）**
1. 第一冲（2 周）：完成用户、食谱、食材、评论、收藏、基本检索接口，数据库基础表完成。
2. 第二冲（2 周）：购物车、书籍聚合、媒体元数据、基础推荐/排行榜与缓存。
3. 第三冲（2 周）：管理/审核、敏感词、审计日志、AI 会话持久化、事件上报管道。
4. 验收与修正（1 周）：联调、性能验证、安全审计、修复。

**风险与注意事项**
- 中文全文检索需要 ES 或者合理选择 MySQL 分词插件，避免直接使用不合适的分词导致检索体验差。
- 媒体文件应使用外部对象存储，数据库仅存元数据；大文件不应保存在 DB。
- 实时推荐/统计使用消息队列解耦，避免同步写影响主业务延迟。
